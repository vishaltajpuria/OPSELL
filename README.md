# OPSELL

A mobile web app for an AI-assisted option-selling strategy on NSE F&O (futures & options) stocks, using your Zerodha account as the data source. It's built to be added to your iPhone home screen so it behaves like a regular app, no App Store needed.

**Where things stand right now:** you can log in with Zerodha and land on the **Strategy** tab, which shows Short/Super Short/Long/Super Long signals from a Supertrend + SMA crossover strategy, in two side-by-side Daily and 4H columns, computed automatically every trading day after market close. Daily covers the **full NSE F&O stock list plus all 5 indices**; 4H covers **indices only** (dropped for stocks — see the batching explanation below for why). **Trade** and **Positions** together let you test the strategy against real (not modeled) option prices without real money — see below. There's also a live option-chain view per stock (strikes, LTP, open interest, any expiry) at `/stocks/[symbol]` — not linked from the bottom nav, since the F&O scanner list that used to link to it was removed, but the route and page still work if you type/bookmark the URL directly.

**How the daily Strategy signals work:** every trading day, four scheduled jobs — Daily at 4:00, 4:05, and 4:10 PM IST, 4H at 4:15 PM IST — fetch historical price data for **every stock in the full NSE F&O universe** (no pre-filtering — see the batching explanation below) plus all 5 indices on Daily, and just the 5 indices on 4H, convert it to Heikin Ashi candles, and check, per stock/index, every adjacent pair in SMA20/50/100/200 (SMA10 is excluded — too close to price, too noisy). Supertrend(14,1) and every SMA are computed on the Heikin Ashi series, not the real candles — this matches how TradingView actually plots them: when a chart's candle type is set to Heikin Ashi, its built-in Supertrend/MA scripts read the HA-transformed open/high/low/close, not the real market prices, unless a script deliberately re-requests raw data. (Earlier versions of this app computed both on real OHLC, which is the textbook-standard way to run Supertrend, but caused a persistent ~5-20 point mismatch against the reference TradingView chart — switching to HA-based calculation closed that gap.) A **short** signal needs all of, on the day the crossover happens: Supertrend is in an uptrend *and was already in an uptrend the day before too*, the Heikin Ashi candle close is still above the Supertrend line, one SMA just crossed from at/below the line to above it, and the *next* SMA out (its target — e.g. SMA50 for a SMA20 cross) is still below the line, meaning only the faster average has caught up so far. The mirror image — Supertrend downtrend (and already downtrend the day before), HA close below the line, an SMA crossing from at/above to below it, target SMA still above the line — is a **long** signal. The "already in that trend the day before" clause specifically excludes the exact day Supertrend itself flips: its value jumps to the opposite band on a flip day (a discontinuity, not a gradual move), so an SMA that happens to already sit past the newly-repositioned line on that same day isn't a genuine crossover — the line jumped past the SMA, not the other way around. This is a real bug that was caught and fixed, not a hypothetical: both PAYTM (Jul 31) and Kaynes Technology (Aug 21) fired signals purely because Supertrend's value reset on the exact day of a trend flip, coinciding with an SMA that had drifted to the far side during the prior trend — neither was a real crossover on a chart. `backtestSymbol` in `lib/backtest.ts` had the identical logic and thus the identical bug, so it's fixed there too — meaning any backtest CSV downloaded before this fix may include some spurious flip-day trades and isn't fully reliable; re-run a backtest to get accurate numbers if you're relying on specific stats from an earlier export. Only the entry price uses the real (non-HA) close, since that's what's actually tradeable. A crossing SMA20 is labeled **Short**/**Long**; a crossing SMA50 or SMA100 (the faster average having already caught up to a slower one) is labeled **Super Short**/**Super Long**.

**A signal keeps showing up for as long as it stays valid, not just on the day it crossed** (`detectSignals` in `lib/strategy.ts`): it isn't enough to check only the latest candle, or a stock would silently vanish from the daily list the day after its crossover even though nothing about the setup had actually broken. Instead, each SMA rung is checked by searching backward from today (up to 90 bars on Daily, 180 on 4H — the same window the backtest tool uses for "still open" trades) for the most recent day the crossover conditions above were true, then confirming that on every day since: Supertrend has stayed on the required side (up for short, down for long) *and* the trigger SMA has stayed on the required side of the Supertrend line. Checking only the Supertrend trend flag isn't enough — Supertrend can stay "up" (price still above the lower band) while the trigger SMA itself pops above the line for a day and immediately falls back below it, a throwback that isn't a full reversal but does mean that specific crossover no longer holds. (Caught via a real case: SMA20 crossed Supertrend for exactly one day, then spent the next three weeks back below it, while Supertrend's own trend label never flipped — the stock kept showing as a live signal that whole time until this was fixed.) If it's genuinely still live, the signal fires today — using today's current entry price, Supertrend value, and SMA values (not the values from the original crossover day), so it's still a decision made off current numbers, just tied to a setup that triggered earlier. This does *not* check whether the target SMA has separately been touched since the crossover — a signal can keep showing even after price has already reached its original target, since that's a different question (would the backtest's own trade simulation have already exited as a win) from whether the setup itself is still structurally intact. The Strategy tab shows just the label, the entry price, and the target price (plus the % distance between them), in two side-by-side Daily and 4H columns — no timestamps or raw Supertrend/SMA numbers, those live in the debug endpoint instead (see below). Within each column, signals are sorted by that entry→target % distance, largest first — the setups pointing at the biggest move surface at the top, rather than hard-filtering by direction or label. (Label was considered as a filter — only showing Super Short/Super Long — but backtesting it against 3 years of real trades showed the opposite of the intuition: Super Short/Long actually underperform regular Short/Long on both win rate and average P&L, since "Super" just means the SMA crossed later, after the move had already run further, not that the setup is stronger. So it isn't used as a filter.)

Four jobs, not one, because of a Vercel Hobby constraint: a function hard-caps at 60 seconds regardless of the `maxDuration` code setting, and at Kite's 3-requests/second historical-data limit, fetching the full ~200-stock F&O universe for one timeframe alone takes about that long in a single invocation — right at the edge of the cap, before indices are even considered. So the **full, unfiltered** stock list is split into 3 alphabetical batches (`BATCH_IDS` in `lib/kv.ts`) for the Daily pass — ~65-70 stocks and well under 20 seconds each — plus one more job for 4H, which now only covers the 5 indices (cheap enough for a single invocation, no batching needed): 3 Daily + 1 4H = 4 jobs total. The 5 indices ride along with Daily's first batch too, so they aren't fetched twice across the Daily batches. See `lib/runDailyStrategy.ts` for the batching/partition logic and `lib/kv.ts` for how each batch's results are stored under their own key and merged into one combined view for the Strategy tab to read.

**Every F&O stock is scanned on Daily, no pre-filtering.** An earlier version narrowed the ~200-stock list down to the ~100 "most promising" candidates before fetching any candles at all (`lib/scanFilter.ts` — a composite liquidity/activity score: near-month futures open interest value, today's futures volume value, today's absolute % move, each ranked by notional ₹ value rather than raw share count so NSE's per-stock lot sizing doesn't distort the ranking), specifically so 2 batches would comfortably fit under Vercel's 60-second cap. That trade-off — trading full stock coverage for smaller batches — is no longer necessary: splitting the *full* list across 3 batches instead of a *filtered* list across 2 fits just as comfortably (see the batching math above), so the filter was dropped from the actual pipeline. `lib/scanFilter.ts` and its ranking logic are still there and still used by the debug endpoint (`/api/strategy/debug/scan-rank?symbol=SYMBOL` while logged in — returns a stock's OI/volume/move percentiles, composite score, and rank within the full list; omit `symbol` for the full ranked list), useful if you ever want to see how "active" a stock was on a given day even though that no longer gates whether it gets scanned. (A near-month futures version of the underlying candle data was tried and reverted — Kite's `continuous=1` futures data is a raw, non-back-adjusted concatenation of monthly contracts, so it carries a real price gap at every rollover; over a 500-day lookback that's compounded across ~16 gaps badly enough to corrupt the ATR/Supertrend math. Spot doesn't have that problem, at the cost of an occasional small Kite-vs-other-data-provider discrepancy on a still-settling candle, which `lib/candleFreshness.ts` mitigates by using the live quote for today's bar.) The app only surfaces short/long calls — turning a signal into an actual option trade (strike, expiry, buy vs. sell) is left to you. You can also trigger all four passes on demand anytime from the **Run strategy now** button on the Strategy tab (it runs them one after another, since they share Kite's rate limit — expect a few minutes total), instead of waiting for the scheduled jobs.

## 1. Get a Zerodha Kite Connect API key

This app needs its own API key to talk to your Zerodha account (this is separate from your regular login).

1. Go to <https://developers.kite.trade/apps> and log in with your Zerodha credentials.
2. Click **Create new app**, choose **Connect** as the type, and give it any name (e.g. "OPSELL").
3. For **Redirect URL**, enter: `https://YOUR-DEPLOYED-URL/api/kite/callback` (you'll get the real URL in step 2 below — you can come back and fill this in afterwards).
4. Kite Connect is a paid API (Zerodha charges a small monthly fee for it, shown on that page) — you'll need to subscribe to use it.
5. Once created, you'll see an **API key** and **API secret**. You'll need both in the next step.

## 2. Deploy the app (no coding required)

The easiest way is [Vercel](https://vercel.com), which is free for personal projects:

1. Sign up at vercel.com (you can sign in with your GitHub account).
2. Click **Add New → Project**, and import this repository.
3. Before deploying, open **Environment Variables** and add:
   - `KITE_API_KEY` — from step 1
   - `KITE_API_SECRET` — from step 1
4. Click **Deploy**. Vercel will give you a URL like `https://opsell-yourname.vercel.app`.
5. Go back to your Kite Connect app settings (step 1) and set the **Redirect URL** to `https://opsell-yourname.vercel.app/api/kite/callback`.

## 3. Connect storage for the daily Strategy job (one-time)

The 4 PM daily routine runs as a scheduled job with no browser attached, so it needs its own small storage to (a) remember you're logged in and (b) save the day's signals for the Strategy tab to show. This is a couple of clicks, no coding:

1. In your Vercel project, go to the **Storage** tab and add a **Redis** database (search the Marketplace for "Redis" if it's not shown directly — it's provided by Upstash and free at this scale).
2. Connect it to this project when prompted — Vercel will automatically add the required environment variables for you (no copying/pasting keys needed for this one).
3. Go to **Settings → Environment Variables** and add one more variable yourself: `CRON_SECRET`, with any random string as the value (this stops strangers from triggering your daily job). A quick way to generate one: run `openssl rand -hex 32` on a Mac/Linux terminal, or just mash the keyboard for 30+ random characters.
4. Redeploy (Deployments tab → latest deployment → **⋯** → Redeploy) so the new variables take effect.

The jobs themselves are already scheduled (see `vercel.json`) — Daily at 4:00 and 4:05 PM IST, 4H at 4:10 and 4:15 PM IST, Monday–Friday. You do need to have tapped **Connect to Zerodha** in the app at some point earlier that same day, since Zerodha's login tokens expire daily and the scheduled jobs re-use whatever session you last logged into.

## 4. Add it to your iPhone home screen

1. Open your deployed URL in **Safari** on your iPhone (must be Safari, not Chrome).
2. Tap the **Share** icon (square with an arrow) in the toolbar.
3. Tap **Add to Home Screen**.

It'll now open full-screen from your home screen like a normal app.

## 5. Using it day to day

- Open the app and tap **Connect to Zerodha** on the Settings tab, then log in with your Zerodha credentials.
- Zerodha access tokens expire every day (usually overnight), so you'll need to tap **Connect to Zerodha** again each trading day — ideally before 4 PM, so the daily Strategy job has a valid session to use. This is a Kite Connect platform behavior, not something the app can silently work around (there's no refresh token in this flow) — miss the reconnect and the first Kite call of the day (often the **Live** button on Positions right at market open) fails with `TokenException`. The app catches that specifically (`KiteAuthError` in `lib/kite.ts`) and turns it into a plain "Your Zerodha session has expired for the day — reconnect from Settings to continue." message with a one-tap **Reconnect** link, instead of surfacing Kite's raw `Incorrect \`api_key\` or \`access_token\`.` string — it also proactively drops the now-dead session cookie server-side (`clearAccessToken` in `lib/session.ts`) so the app stops claiming to be connected.
- Browse F&O stocks and tap one to see its option chain for the nearest expiry (you can switch expiries from the dropdown).
- Check the **Strategy** tab after market close for that day's short/long signals.
- Use the **Trade** tab to act on a signal — pick Buy or Sell on a candidate, review the live quote, confirm with however many lots. Check the **Positions** tab for what's open, and hit its **Live** button whenever you want an updated mark-to-market.

## Paper trading

Two tabs, split deliberately: **Trade** (`/paper`, `components/PaperTradeCandidates.tsx`) is where you act on a signal, **Positions** (`/positions`, `components/PaperTradePositions.tsx`) is where you track what's open — kept apart so a long candidate list on Trade never buries your open positions below the fold, which is what happened when both lived on one page. Both act on real, live option prices — not the backtest tool's Black-Scholes estimates — without placing a real order. Everything is manual: nothing opens or closes on its own.

**Trade**'s candidates are today's Daily signals from the same `signals:latest` data the Strategy tab reads (4H isn't included here, to start simple), sorted by entry→target % distance largest-first — same reasoning as the Strategy tab's own sort: the setups pointing at the biggest move surface first. For each one, tap **Buy option** or **Sell spread** to preview a concrete trade — real strike, real expiry, real current premium, fetched fresh from Kite's option chain — then enter how many lots and **Confirm**. The preview is re-resolved from scratch at confirm time (not reused from whenever you were looking at it), so the recorded entry price is always just-fetched, not stale.

**Trade any scrip** (`components/ManualTradePanel.tsx`, at the top of the Trade tab) opens the exact same preview/confirm flow — live pricing, the strike picker, everything — on any F&O stock or index, not just today's strategy candidates. Search picks a symbol from `/api/instruments` (every F&O stock plus NSE's index F&O names; SENSEX is left out since it trades on BSE and this app only fetches NFO option data), then you choose **Long**/**Short** directly (there's no algorithmic signal for an arbitrary scrip to derive it from) before **Buy option**/**Sell spread** — the same directional mapping a strategy signal's direction would otherwise drive. This doesn't change or add to the strategy's own signal list in any way; it's a separate entry point into the same paper-trading machinery.

Underneath the entry→target line, a candidate also shows its **next gap** when it has one within 20% of entry price — e.g. `Next gap 1,842.50 (-6.2%)`. This is a real price gap (raw OHLC, *not* Heikin Ashi — a gap is a genuine market phenomenon, empty space nobody actually traded through, unlike the Heikin Ashi candles the strategy's own crossover detection runs on) that price hasn't yet traded back into since it formed (`findNextGap` in `lib/gaps.ts`, computed once per stock alongside the daily strategy scan — see `lib/runDailyStrategy.ts`). It's purely informational: **it never filters or ranks the signal list** — the same crossover strategy as always decides what shows up here, this just adds one more data point about a candidate that already made the cut. An unfilled gap-up always sits below the current price (shown as a negative %, a support/pullback level) and an unfilled gap-down always sits above it (positive %, a resistance/rally level) — that's a property of what "unfilled" means, not something hardcoded. No line is shown at all if there's no unfilled gap within 20%, or for 4H signals (no raw daily candles are fetched during that pass to compute one from).

**Buy** is a naked, purely directional bet aligned with the signal's expected move: a **Long** signal (expecting a reversal up) buys a **call**, a **Short** signal (expecting a reversal down) buys a **put** — at the ATM strike (closest available strike to the current spot). This is deliberately the *opposite* mapping from selling, since buying bets the move happens rather than betting it doesn't.

**Sell** builds a credit spread, same mean-reversion mapping as the backtest's option-selling mode (Long signal sells a put, Short sells a call): the short leg picked at ~1% OTM, a protective long leg at least 4% OTM (naturally landing near 4-5% given typical NSE strike spacing — see `pickOtmAtLeast` in `lib/paperTrading.ts`). Net entry premium is the short leg's premium minus the long leg's.

Once a fresh (not "adding to existing") preview is up, either mode offers **"Choose strike(s) myself"**, replacing the auto-picked leg(s) with a live option chain — one dropdown for a buy (just the ATM leg), two for a sell (short/long) — each option listing a strike alongside its live mid-price, flagging one with `no live bid/ask` or a wide `X% spread` so an illiquid strike is visible before you trade it, not after. Picking a strike re-prices the preview against a fresh quote for exactly that leg. Whichever strike(s) are showing when you hit **Confirm** — auto-picked or chosen — are exactly what gets opened, since `/start` is told to use them rather than re-picking automatically (spot can move between preview and confirm, so this also makes buy-mode confirms match their preview, not just sell-mode ones).

**Pricing uses bid/ask mid, not last-traded price**, everywhere a premium is read — option-chain rows, a trade plan's premium, and a Live-button mark-to-market (`quoteMidPrice` in `lib/kite.ts`, from Kite's order-book depth on the same `/quote` call already being made — no extra API round-trip). A strike's *last trade* can be hours old at a very different underlying level once a strike goes illiquid or far OTM, which is exactly what produces "impossible"-looking readings like a further-OTM option pricing higher than a closer one; the live best-bid/best-ask mid reflects what's actually quoted right now instead. Falls back to last-traded price only when a strike has no resting bid or ask at all. The option-chain view (`/stocks/[symbol]`) shows both — mid as the primary figure, last-traded price underneath in small text whenever it differs from mid — so the gap itself is visible.

**Expiry**: the current month's monthly contract, unless fewer than 12 trading sessions remain until it — then it rolls to next month's. "Monthly" here is derived from real instrument data (the latest expiry occurring within each calendar month, so it correctly picks the true monthly contract for an index even though indices also have weekly expiries), not a naive last-Thursday-of-month calendar formula. "Trading sessions remaining" is a weekday-only approximation (no NSE holiday calendar) — occasionally off by a session or two around a market holiday.

**Weekly expiry, NIFTY only**: once a fresh (not "adding to existing") preview is up for NIFTY, a **Monthly**/**Weekly** toggle appears next to the expiry line. Weekly trades the nearest upcoming expiry instead of the monthly contract (`pickWeeklyExpiry` in `lib/paperTrading.ts`) — no 12-session rollover the way monthly has, since a weekly contract is short-dated by design and the nearest one IS the point of choosing it. Switching re-prices against a fresh quote and clears any manually-chosen strikes from before the switch (a strike picked off one expiry's chain doesn't carry over to a different one's). This is deliberately restricted to NIFTY — its weeklies are consistently NSE's most liquid weekly F&O contract, which the auto-picked strikes' bid/ask quality depends on; trying it on any other symbol is rejected server-side (`buildTradePlan`) with a clear error, not silently priced against something illiquid.

**The Live button** re-fetches current quotes for every open trade's option leg(s) (batched into as few Kite calls as possible) and updates the shown mark-to-market P&L — it never closes anything on its own. Closing a trade is its own button, any time, on any open position: it fetches one more live quote, records the exit premium, and marks the trade closed.

**Adding to or trimming a position** (`Add`/`Reduce` on each open position, Positions tab): a position isn't just open-then-fully-closed — you can top it up or partially close it any number of times over its life.
- **Add** fetches a live quote for the position's *existing* strike(s) — never resolves a fresh ATM/OTM strike — and blends it into the entry premium as a lots-weighted average, same as a real broker averaging in a top-up (`weightedAveragePremium` in `lib/paperTrading.ts`). This is also what happens automatically from the **Trade** tab: if a symbol you tap Buy/Sell on already has an open position in that mode, the preview shows "adding to existing position" and reuses its strike instead of pricing a brand-new one at today's spot (`/api/papertrade/preview` checks `findOpenTrade` first) — the whole reason this exists is that today's ATM/OTM strike can differ from the one you're already holding, and adding at a different strike wouldn't really be "the same position."
- **Reduce** (or the plain **Close** button, which is just "reduce by everything that's open") splits off however many lots you specify, realizes P&L on just that portion at a fresh live quote, and leaves the rest open at its *unchanged* entry premium — a partial close doesn't reprice what's still open. Capital is split between the closed and remaining portions by simple proportional scaling of the pre-close `capitalRequired` (`computePartialClose`), not a fresh margin call each time — margin is close enough to linear per lot for the *same* contract at a different quantity that this is accurate without the extra API round-trip.
- Each add/reduce is its own event (`ClosedLot[]` on the trade, see `lib/kv.ts`) — a position topped up and trimmed several times over a few weeks has one entry per trim, each dated when it actually happened, which is what the Performance tab's monthly buckets are built from. The Positions tab's **Closed** list, though, groups these events for *display* by exact contract (same symbol, mode, and leg(s) — a different strike, or a different expiry at the same strike, stays its own row) so a position closed in several tranches — or reopened later at the identical strike — reads as one combined realized P&L instead of a separate line per trim. This is purely a display grouping: Performance's monthly buckets still work off the individual underlying events, unaffected by how Positions chooses to group them for the list.
- **Duplicate positions** (same symbol/mode/strike(s) recorded as two separate open trades — e.g. from opening the same position twice before the `/start` guard existed) are detected client-side and surfaced as a "Merge" banner at the top of Positions. Merging (`POST /api/papertrade/merge`, `findDuplicateOpenGroups`/`mergeOpenTradeGroup` in `lib/paperTrading.ts`) sums the lots, blends the entry premium as a lots-weighted average, concatenates both records' `closedLots` history so no realized P&L is lost, and re-prices `capitalRequired` fresh for the combined size rather than summing two possibly-stale margin figures.

**Capital deployed**, shown as one total at the top of Positions plus a per-position figure: for a **buy**, it's just the premium paid — always known, no API call needed. For a **sell** spread it's the real hedge-aware margin Kite's basket-margin endpoint (`getBasketMargin` in `lib/kite.ts`, `POST /margins/basket`) would actually require for holding both legs together as one basket, held as NRML since a paper position isn't auto-squared off intraday — not a hand-rolled SPAN/exposure estimate. This is computed once, at entry, and never re-fetched by the Live button, so it stays a fixed denominator if you're tracking return on capital deployed over time rather than a number that drifts underneath you as margin requirements move. If the margin lookup fails for some reason, that position's capital is left `null` (and flagged as excluded) rather than silently being counted as ₹0 and understating the true total — the **Live** button opportunistically retries it for any open trade that's still missing one (`backfillCapitalRequired` in `lib/paperTrading.ts`), which is also what fills it in for a trade opened before this field existed at all (it has no such field in storage, not a failed lookup, but shows the same "unknown" until refreshed once).

Each position on the Positions tab also shows its **direction** (`Short`/`Long`, colored red/green — same convention as the Strategy and Trade tabs) next to the symbol, and, for a **sell** spread specifically, its **max profit / max loss** (colored green/red): max profit is the net credit collected if both legs expire worthless, max loss is that credit minus the strike width, hit once the underlying moves past both strikes (`spreadMaxProfitLoss` in `components/PaperTradePositions.tsx`) — both scaled by the position's current lots, so they update as you add to or trim it. Not shown for naked buying, where loss is already capped at the premium paid (the capital figure above) and profit is uncapped.

**Today's P&L** — a stat card at the top of Positions, plus a per-position figure — is the day's move, separate from a position's whole-life P&L shown alongside it. It combines two things: for still-open positions, the day's mark-to-market change (`computeTodayPnl` in `lib/paperTrading.ts`) — measured from each leg's previous close (Kite's own `ohlc.close`, already on every quote) to its current price if the position was opened before today, or from its entry premium if opened today (there's no "yesterday" to measure from yet); and for anything actually closed (fully or partially) today, its full realized P&L, which needs no live refresh since it's already fixed. A position topped up today after being opened earlier is measured uniformly from the earlier reference point across its whole size — a documented approximation, since per-lot entry dates aren't tracked separately from the single weighted-average entry premium. **Like every other live figure here, this only updates when you hit Live** — it's computed and persisted (`todayPnl` on the trade, `lib/kv.ts`) during that same refresh, not recalculated on every page load, so it reflects the last time you pressed Live, not necessarily right now.

Each open position also shows the **underlying stock/index's own current price and today's move** — ₹ value and %, with a ▲/▼ arrow, colored green/red — right under its header line. This is deliberately a different number from Today's P&L above: it's "how is the stock itself doing today," independent of which way the option position is betting (a short position profits when the stock is red). Same previous-close math as Today's P&L (`markToMarket` in `lib/paperTrading.ts`, extended to also return the underlying's change alongside the option premium) and the same "only updates on Live" rule — the price itself is known from the moment a position opens, but the day-change needs a live quote's previous close, so it shows "hit Live to refresh" until the first refresh.

### Performance tab

`/performance` (`lib/performance.ts`'s `computePerformance`, a pure function over whatever's currently in the paper-trade ledger — no separate cache, so it's always current the moment a position is closed, in full or in part) turns realized P&L into monthly and cumulative returns.

The unit of reporting for **P&L** is a **close event**, not a position — every `Add`/`Reduce`/`Close` on a position that actually realizes something appends one entry to that trade's `closedLots` (see above), and each entry counts toward the month it happened in (`closedAt`), independently. A position added to and trimmed three times over two months contributes to however many of those months it was actually trimmed in, at that trim's own P&L — not one lump sum attributed to whenever it finally reaches zero. An open position's mark-to-market never affects a month's return (shown separately, as a single "currently unrealized" note, since it can still move either way before you actually close it).

A month's return % is realized P&L divided by the **peak total capital the whole portfolio actually had deployed at any single point in time during that month** (`maxCapitalDeployed`), not a sum of what happened to release that month — summing overstates it whenever multiple non-overlapping positions each release their own capital in the same month (you never had all of it deployed at once — closing one, then opening and closing another, uses the same capital twice, not double the capital), and understates it whenever a position stays open past month-end (its capital was fully at risk all month even though it hasn't released anything yet to sum). This is reconstructed from a per-trade **capital ledger**: every trade now logs a `capitalHistory` entry (`{at, capitalRequired}` — `lib/kv.ts`) whenever its own capital level actually changes (opened, added to, partially or fully closed — see the relevant route in each case), and `buildCapitalTimeline` (`lib/paperTrading.ts`) sweeps every trade's history in chronological order to produce one combined step-function of the portfolio's total capital-in-use over time; `maxCapitalInRange` (`lib/performance.ts`) then takes the peak of that step-function within a month's date range, including whatever level was already carried in from before the month started. The **overall** figure uses the same timeline's peak across the *entire* history (including right now, if a position is still open) rather than a sum across all months. Trades from before this ledger existed get a best-effort single- or two-point history synthesized from what's already on the record (`synthesizeCapitalHistory` in `lib/kv.ts`) — an approximation for old data only; every trade going forward gets an exact record. Merging duplicate positions (see above) reconstructs the pre-merge combined timeline the same way, rather than losing history or double-counting it.

**Capital growth** is shown two ways: cumulative realized P&L over time (a running total by month, with a proportional bar, still an absolute ₹ figure with no assumed starting capital) and, separately, **portfolio value against a capital base** — a fixed reference point (default ₹50,00,000, `getCapitalBase`/`setCapitalBase` in `lib/kv.ts`, stored under `papertrades:capitalBase` and editable inline on the Performance tab via `CapitalBaseEditor`). The base only feeds `returnOnBasePercent` (P&L as a % of the whole book, per month and overall) and the portfolio-value view (`capitalBase` + cumulative realized P&L by month, plus a live `currentPortfolioValue` snapshot that also folds in current open positions' unrealized P&L) — it never changes the max-capital-based `returnPercent` figures described above, which stay based on peak capital actually deployed, not the base.

**P&L sign convention** (`computePnlPerShare` in `lib/paperTrading.ts`, same as the backtest's option-selling code): buying profits when the premium rises above what you paid; selling profits when it falls below what you collected. Positions are stored as one JSON list in Redis (`papertrades:all` — see `lib/kv.ts`) since entries/exits are manual and low-volume, unlike the daily/4H signal cache's sharded batch keys.

One real gap: **SENSEX options aren't reachable here** — they trade on the BSE, not NFO, and this app only fetches the NFO instrument dump (see `lib/instruments.ts`). Trying to trade a SENSEX signal will fail with a clear error rather than silently doing the wrong thing, but it isn't supported.

## Backtesting the strategy

There's a `/backtest` page (not in the bottom nav — open it directly by URL) for checking how a strategy would have performed historically on any list of stocks *or indices* you choose, on **Daily, 4H, and/or 2H — pick any combination, not just one at a time.** Paste in symbols (e.g. today's top stocks by market cap — Kite's Watchlist can sort by market cap — or index keys: NIFTY, BANKNIFTY, FINNIFTY, MIDCPNIFTY, SENSEX), tap however many timeframe buttons you want selected, and it fetches candles per (symbol, timeframe) pair and walk-forward simulates every signal the strategy would have fired, not just the latest one. Results are grouped into a separate labeled section per selected timeframe, each with its own summary/per-stock/trade-list, so you can directly compare the same symbols across timeframes in one run. The CSV export includes every selected timeframe's data in one file (a `Timeframe` column, plus a labeled summary block per timeframe up top). Index symbols are resolved via `getIndexToken()` (same one the Strategy tab's index runs use) instead of `getEquityToken()` — the route (`app/api/strategy/backtest/route.ts`) checks each pasted symbol against `INDEX_DEFS` from `lib/indices.ts` first and falls back to the equity lookup.

**Two selectable strategies**, both run through the same page (symbols, timeframes, stop loss, option-selling modeling all work the same way for either):
- **Supertrend + SMA** (`lib/backtest.ts`) — the same Supertrend(14,1) + SMA20/50/100/200 crossover logic as the Strategy tab, short and long. See the walk-forward simulation rules documented in that file.
- **RSI Double Dip** (`lib/rsiDipBacktest.ts`) — a long-only strategy ported from a community Pine Script ("RSI & SuperTrend Özel Dip Stratejisi"): RSI(10) crossing above its own 10-period SMA counts as a qualifying "dip" whenever RSI is still below 50 (crossing back above 50 resets the count to zero); the 2nd such crossover — a double-bottom shape in the oscillator — fires a long entry at the next bar's open. The position exits on the first bar Supertrend(10, 2.5) transitions from an uptrend to a downtrend (a single-bar flip event, not "whenever it's in a downtrend" — matching the source script's `ta.change(direction) > 0` exactly). Computed on real OHLC candles, not Heikin Ashi, since the source script never requests it. There's no target exit and no stop-loss in the original script; an optional fixed stop-loss % is offered in the UI anyway, for parity with the other strategy, but it's off by default. The strategy's parameters (RSI length, signal length, trigger level, cross count, Supertrend period/multiplier) are hardcoded to the script's own defaults, not exposed as UI knobs. Being long-only, the Direction filter control is hidden for this strategy, and in option-selling mode it always sells puts (never calls).

**Timeframe** matters for how much history is available, not just candle size: Daily fetches ~5.4 years of calendar days (Kite's cap on a single "day"-interval request is ~2000 days), giving roughly **4.6 years** the strategy can actually fire signals on, after the ~210-bar SMA200/Supertrend warm-up eats into the front of the range. Going further would need chunking multiple requests per symbol, which isn't done. 4H and 2H are resampled from 60-minute candles (`resampleTo4H`/`resampleTo2H` in `lib/indicators.ts`, session-anchored — the last bar of each day is short rather than calendar-aligned), and Kite's historical endpoint caps 60-minute-interval requests to ~400 days regardless of what's requested, so intraday backtests only cover roughly the last 13 months — that ceiling doesn't move with the daily lookback.

Each selected timeframe needs its own historical request per symbol, so the request count is `symbols × timeframes selected` — not a flat per-symbol count anymore. The UI's soft cap is 150 total requests (e.g. up to 150 symbols on one timeframe, or up to 50 symbols with all three selected), enforced client-side with a message telling you the max symbol count for your current timeframe selection; the route (`MAX_WORK_ITEMS`, currently 300) hard-caps the same thing server-side as a safety net.

Two things scale with the chosen timeframe rather than staying fixed, since a "bar" means a different amount of real time on each one:
- The unresolved-trade cutoff (~90 bars, previously always ~90 calendar days) scales up on intraday timeframes so it still covers roughly the same real-world window — ~180 bars on 4H, ~360 on 2H — instead of quietly becoming "~45 days" or "~22 days" just because a bar is smaller.
- In option-selling mode, the realized-volatility estimate's window and annualization factor scale the same way (`volWindowBars`/`periodsPerYear` in `lib/optionsBacktest.ts`) — annualizing intraday bar-to-bar returns with the daily 252-per-year factor would understate volatility by roughly √(bars-per-day), since each bar only reflects a fraction of a day's actual movement.

Fetches run batched at Kite's 3 requests/second historical-data limit (`lib/rateLimit.ts`, shared with the daily/4H strategy run) rather than one at a time, so e.g. 100 symbols takes roughly 35 seconds, not 100+. The 150-symbol soft cap in `components/BacktestRunner.tsx` exists because Vercel Hobby hard-caps a function at 60 seconds — past ~150-170 symbols in one run, that budget gets tight; split a bigger list into two runs instead.

Since the target is a moving SMA line, not a fixed price, the simulation has to make a few calls about how a trade actually plays out — worth knowing before trusting the numbers:
- Entry is the next day's open after a signal (the signal itself is only known once that day's candle closes — entering at that same day's close would be lookahead bias).
- A trade exits the first day price actually touches the target SMA's *current* value (checked against that day's low for a short, high for a long) — the target moves with the SMA each day, exactly as you described.
- The optional "Stop loss %" field adds a fixed price stop (checked against that day's high for a short, low for a long), checked first each day, ahead of the target — a day where both would technically trigger is conservatively treated as a stop-out. Leave it blank to skip this and rely only on the next rule.
- If neither the stop loss nor the target is hit, the trade exits the first day Supertrend flips against the position, at that day's close — the strategy's own signal that the setup broke, used here as a second, unbounded stop-loss rule since the strategy itself is signal-only and doesn't define one.
- Only one trade per stock at a time — a new signal while a trade is already open is ignored until that trade exits.
- A trade neither hit nor invalidated within ~90 trading days (or still running when the data runs out) is marked "open", excluded from the win/loss rate rather than forced into either bucket.
- The **Direction** selector (All / Short only / Long only) restricts which signals get taken at all — the excluded direction isn't just filtered from the results, it's skipped during detection, so an excluded long signal doesn't block a later short one from firing on the same stock. Useful since large-cap NSE stocks tend to drift upward over multi-year windows, which structurally favors longs in an unfiltered backtest — Short only isolates whether the short side holds up on its own.

See the doc comment on `backtestSymbol()` in `lib/backtest.ts` for the full reasoning — these are reasonable defaults, not something the strategy itself specifies, so it's easy to point back to this if a number looks off and you want a rule changed.

### Modeling it as option-selling instead

The **"Model as option-selling"** checkbox turns each stock- or index-level trade into what selling an option against that same signal would have looked like: a long signal sells a ~3% out-of-the-money put, a short signal sells a ~3% OTM call, both expiring on the near-month NSE **monthly** expiry (rolls to next month if the signal fires after that month's expiry already passed) — `nearMonthExpiry()` always computes the last Thursday of the month and never touches a weekly expiry date, so this holds for indices too even though NIFTY/BANKNIFTY etc. also have weekly contracts in real life. The option is priced with the Black-Scholes formula (`lib/optionsPricing.ts`) using volatility estimated from the underlying's own trailing 20-day realized volatility as a stand-in for implied volatility, since Kite doesn't reliably retain historical data for expired option contracts the way it does for the underlying — **these are modeled estimates, not real historical option prices.** If the underlying trade's own exit (target/stop/Supertrend-flip) would land after that month's expiry, the option is instead settled at expiry using intrinsic value only, matching real expiry mechanics (`lib/optionsBacktest.ts`'s `toOptionTrade()`).

Results are reported in **₹ per share, not %** — % of a small, far-OTM premium can swing to numbers like -20,000% on a single bad trade (mathematically correct — a naked option seller genuinely can lose many multiples of the tiny premium collected — but useless for averaging across trades), so ₹ terms are what's aggregated and compared. Sanity-tested against synthetic price paths before shipping: selling into a rally decays a put toward worthless (positive ₹ P&L), selling into a crash blows the same put's value up far past what was collected (a large negative ₹ P&L, correctly uncapped), and an unresolved trade correctly settles at expiry using intrinsic value.

An optional **"Spread width %"** field (shown once option-selling mode is on, defaults to 4) turns the naked short into a credit spread: a second, protective leg is bought further OTM — short leg stays ~3% OTM, long leg sits at ~3%+width% OTM, both same expiry. The max loss per trade becomes capped at (strike width − net credit collected), shown per-trade and as an "Avg capped max loss" summary line, instead of the naked short's unbounded downside. Leave the field blank to go back to naked. Verified against the earlier naked-crash sanity case: the same crash that cost the naked put ₹127.89/share cost the 4%-wide spread only ₹37.81/share — exactly matching its own computed max loss, confirming the cap holds even when the underlying blows straight through both strikes.

## Notes for whoever maintains this later

- Built with Next.js 14 (App Router) + TypeScript + Tailwind CSS.
- Talks to Kite Connect directly over `fetch` (no third-party Kite SDK), to avoid pulling in that SDK's outdated, vulnerable transitive dependencies.
- The instrument dump is cached in memory per server process for 6 hours; on serverless hosts each cold start refetches it once.
- `lib/indicators.ts` / `lib/strategy.ts` hold the Supertrend + SMA math and crossover detection, kept as pure functions over candle arrays — no I/O, easy to unit test in isolation.
- `lib/runDailyStrategy.ts` exports two independent functions. `runDailyTimeframeStrategy(accessToken, batchId)` takes a `batchId` ("A"/"B"/"C" — see `BATCH_IDS` in `lib/kv.ts`) that selects which alphabetical slice of the **full, unfiltered** F&O stock list to process (`partitionForBatch`), plus all 5 indices alongside batch "A". `run4HTimeframeStrategy(accessToken, batchId)` still takes the same `BatchId` type for a uniform route/cron shape, but only does real work for `batchId === "A"` — it's indices-only now (no stock loop at all), 5 symbols being cheap enough for one invocation. Each is shared between its own cron route (`app/api/cron/daily-strategy` / `-4h`, both reading `?batch=` from the query string) and its own manual endpoint (`app/api/strategy/run` / `run-4h`, same query param) behind the Strategy tab's button. All four jobs (Daily A/B/C + 4H A) are rate-limited to Kite's 3 req/sec historical-data cap in batches of 3 and checkpoint-save after their stocks phase so an indices-phase timeout doesn't lose that invocation's run. `maxDuration` is set to 300s on each route, but Vercel's Hobby plan hard-caps actual function duration at 60s regardless — which is exactly why the work is split into multiple invocations instead of 1; upgrading to Pro removes that cap (at which point `BATCH_IDS` could shrink back to a single batch, and 4H stocks could be reinstated if wanted). `lib/kv.ts`'s `saveSignalBatch()` writes each (date, timeframe, batchId) combination to its own Redis key and republishes a merged view across all of them, so batches that run minutes apart in separate function invocations with no shared memory can't clobber each other. Since that merge unconditionally reads every `BATCH_IDS` entry regardless of whether anything wrote to it today, `run4HTimeframeStrategy`'s batch-"A" call also explicitly writes an *empty* signal list to every other `BATCH_IDS` entry's 4H key for today — otherwise any stock signals a batch B/C 4H run had already written before this change shipped (or from a stray old cron trigger still pointed at a since-removed batch) would keep showing up merged into `signals:latest` forever, since nothing would ever overwrite that specific key again.
- `package.json` doesn't pin `package-lock.json` — it's regenerated deterministically by `npm install`.
- `app/strategy/page.tsx` reads whatever the daily job last stored; it doesn't compute anything itself.
